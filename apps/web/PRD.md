# PRD: Main App (`apps/web`)

## 1. Назначение приложения

`apps/web` — это основное демонстрационное приложение, цель которого:

- показать использование UI Kit в продуктовой среде;
- продемонстрировать архитектуру SPA с TanStack Router;
- подтвердить, что UI Kit пригоден не только для docs, но и для реальных сценариев.

Приложение используется:

- как часть портфолио;
- как “тестовое задание”;
- как интеграционный клиент UI Kit.

---

## 2. Архитектурная роль в системе

`apps/web` — потребитель UI Kit, но не источник истины.

Он:

- использует компоненты и types из `@repo/ui-kit`;
- не определяет props, `states` или контракты;
- не хранит копии спецификаций.

Любые изменения API компонентов начинаются в `packages/ui-kit`, а не здесь.

---

## 3. Технологический стек

- React
- TanStack Router
- Vite (как dev/build tool)
- TypeScript

Приложение не использует:

- backend;
- базу данных;
- auth;
- server-side rendering.

---

## 4. Роутинг (TanStack Router)

### 4.1 Требования к маршрутам

Приложение обязано иметь минимум 3 маршрута:

1. `/`
   - Landing / overview
   - краткое объяснение назначения проекта
2. `/form`
   - форма с использованием компонентов UI Kit
   - демонстрация controlled inputs + submit
3. `/ui` (или `/components`)
   - композиция компонентов
   - пример “как UI Kit выглядит в продукте”

### 4.2 Типобезопасность

TanStack Router должен использоваться с:

- типизированными маршрутами;
- типизированными search params **или** loader’ом (минимум один пример).

Цель: показать, что “роутинг — часть типовой архитектуры, а не строковые пути”.

---

## 5. Использование UI Kit

### 5.1 Правила импорта

Разрешено только:

```ts
import { Button, Input, states } from "@repo/ui-kit";
```

Запрещено:

- импортировать внутренние файлы `ui-kit`;
- копировать компоненты или `states` в `apps/web`.

### 5.2 Роль states в main app

`states` не используются напрямую как UI (в отличие от docs), но могут:

- служить примерами корректных значений;
- использоваться в тестах или моках;
- применяться как reference для разработчика.

---

## 6. UX-сценарии (минимум)

### 6.1 Форма (обязательный сценарий)

Форма должна:

- использовать минимум 2 компонента UI Kit (например: `Input` + `Button`);
- иметь controlled state;
- демонстрировать disabled / loading / error состояние кнопки.

Допустимо (но не обязательно):

- использовать Valibot для валидации формы;
- показать соответствие формы контрактам компонентов.

### 6.2 Композиция компонентов

Один экран должен показать:

- несколько компонентов UI Kit в композиции;
- базовый layout (Card / Stack / Section — если есть);
- реалистичный, но простой UI.

Цель — показать, что UI Kit:

- масштабируется;
- не выглядит “storybook-only”.

---

## 7. Ограничения и намеренные упрощения

Приложение намеренно упрощено:

- нет сложного состояния;
- нет API-запросов;
- нет сложной бизнес-логики.

Это сделано, чтобы:

- не отвлекаться от архитектуры UI;
- не маскировать качество UI Kit “фичами”.

---

## 8. Инварианты и запреты

Запрещено:

- определять собственные UI-компоненты, дублирующие `ui-kit`;
- расширять props компонентов локально;
- хранить `states` в приложении как источник истины;
- усложнять роутинг без архитектурной необходимости.

---

## 9. Критерии готовности (DoD)

`apps/web` считается корректным, если:

1. Приложение запускается через `pnpm dev`.
2. Реализованы минимум 3 маршрута.
3. Используется TanStack Router с типизацией.
4. UI Kit используется исключительно через публичный API.
5. Есть форма и пример композиции компонентов.
6. Приложение читаемо и легко объясняется за 5 минут.

---

## Appendix: формулировка для собеса
