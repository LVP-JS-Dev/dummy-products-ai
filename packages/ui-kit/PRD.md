# PRD: UI Kit (`packages/ui-kit`)

## 1. Назначение пакета

`ui-kit` — это переиспользуемая UI-библиотека, являющаяся:

- формальной спецификацией UI-компонентов;
- источником типизированных контрактов;
- поставщиком валидных состояний (`states`);
- генератором машиночитаемой UI-спецификации.

Пакет предназначен для использования:

- в основном приложении (`apps/web`);
- в документации (`apps/fumadocs`);
- потенциально — ИИ-агентами и инструментами.

---

## 2. Архитектурная роль в системе

`ui-kit` является ядром монорепозитория.

Все остальные части системы:

- потребляют `ui-kit`;
- не определяют API компонентов;
- не хранят собственные версии контрактов или `states`.

Нарушение этого принципа считается архитектурной ошибкой.

---

## 3. Публичный API пакета

### 3.1 Экспортируемые сущности

`ui-kit` обязан экспортировать через `src/index.ts`:

1. **Компоненты**
   - React-компоненты (например: `Button`, `Input`).
2. **Типы props**
   - типы, выведенные из контрактов (например: `ButtonProps`).
3. **States**
   - экспортируемые как единый namespace:

```ts
import { states } from "@repo/ui-kit";
```

### 3.2 Запрещённые практики

- Прямой импорт внутренних файлов:

```ts
import Button from "@repo/ui-kit/src/components/Button";
```

- Дублирование props или `states` в приложениях или docs.
- Экспорт “временных” или нестабильных API без отражения в PRD.

---

## 4. Контракты компонентов (Contract-first)

### 4.1 Контракт как источник истины

Каждый компонент обязан иметь формальный контракт:

- файл: `src/contracts/<name>.contract.ts`;
- контракт описывает:
  - shape props;
  - допустимые варианты (union / enum);
  - optional / required поля;
  - базовые ограничения (где применимо).

Контракт не зависит от React.

### 4.2 Типы props

Тип props компонента:

- выводится исключительно из контракта;
- не объявляется вручную.

Прямое определение интерфейсов props вне контракта запрещено.

### 4.3 Изменения контракта

Любое изменение контракта:

- автоматически считается изменением публичного API;
- требует:
  - обновления компонента;
  - обновления `states`;
  - обновления generated-артефактов;
  - обновления документации (если применимо).

---

## 5. Components

### 5.1 Назначение компонентов

Компоненты:

- реализуют отображение;
- используют props из контракта;
- не валидируют входные данные самостоятельно (валидация — ответственность контракта и тестов).

### 5.2 Ограничения

Компоненты не должны:

- содержать бизнес-логику;
- зависеть от документации или docs-специфичных библиотек;
- изменять shape props, определённый контрактом.

---

## 6. States (fixtures) как часть системы

### 6.1 Назначение states

`states` — это формальные, валидные примеры использования компонента.

`states` используются:

- для документации;
- для визуализации;
- для тестов;
- для агентного потребления.

`states` — публичный API, а не вспомогательные примеры.

### 6.2 Формат states

Для каждого компонента:

- файл: `src/states/<name>.states.ts`;
- формат:

```ts
export const buttonStates = {
  Primary: { /* ... */ },
  Secondary: { /* ... */ },
  Disabled: { /* ... */ },
} as const;
```

### 6.3 Требования к states

- Минимум 3 состояния:
  - `default`;
  - `variant`;
  - `edge-case`.
- Data-only:
  - без React;
  - без функций;
  - без side-effects.
- Каждое состояние обязано проходить валидацию контрактом.

### 6.4 Экспорт states

Все `states` агрегируются в `src/states/index.ts` и экспортируются как единый namespace:

```ts
export const states = {
  button: buttonStates,
  input: inputStates,
} as const;
```

## 7. Генерация машиночитаемой спецификации

### 7.1 Назначение

`ui-kit` генерирует артефакты, предназначенные для:

- агентного потребления;
- инструментов;
- автоматической валидации.

### 7.2 Артефакты

Скрипт `pnpm gen` обязан генерировать:

- JSON Schema для каждого контракта: `src/generated/schemas/<component>.schema.json`;
- `manifest.json`: `src/generated/manifest.json`.

### 7.3 Manifest (MVP)

Минимальный формат:

```json
{
  "components": {
    "Button": {
      "schema": "schemas/button.schema.json"
    }
  }
}
```

Manifest является точкой входа для внешних инструментов.

---

## 8. Контрактные тесты

### 8.1 Назначение тестов

Контрактные тесты гарантируют:

- валидность `states`;
- отсутствие рассинхронизации между контрактами и примерами.

### 8.2 Обязательные проверки

`pnpm test` должен:

- проверять каждое state-значение соответствующей схемой;
- падать при любом несоответствии.

---

## 9. No-drift правило

### 9.1 Generated-артефакты

`src/generated/**` является частью репозитория и коммитится.

### 9.2 Проверка

Команда `pnpm check` обязана:

1. запустить генерацию (`gen`);
2. запустить тесты;
3. убедиться, что `git diff` пустой.

Любой drift считается ошибкой.

---

## 10. Invariants и запреты (критично)

Запрещено:

- изменять компонент без изменения контракта;
- добавлять `states` без валидации;
- использовать `states` только для docs, но не экспортировать их;
- добавлять docs-зависимости в `ui-kit`;
- хранить “частные” props или состояния вне контракта.

---

## 11. Эволюция пакета

Допустимо в будущем:

- расширять `manifest.json` (intent, category, a11y, tokens);
- добавлять новые компоненты;
- добавлять новые `states` для существующих компонентов.

Недопустимо:

- менять философию contract-first;
- превращать `states` в “демо-примеры” без формальной роли.

---

## 12. Критерий готовности (DoD)

`ui-kit` считается корректным, если:

1. Каждый компонент имеет контракт.
2. Каждый контракт имеет `states`.
3. Все `states` валидируются тестами.
4. `manifest.json` и schemas актуальны.
5. Пакет используется через публичный API.
6. Docs и apps не дублируют спецификацию.

---

## Appendix: короткая формулировка для собеса

> UI Kit у нас contract-first: контракты — источник истины, states — часть публичного API, docs и приложения — клиенты. Это позволяет держать UI как формальную, машиночитаемую систему.
