# Design

## Context

`apps/web/src/routes/products.tsx` сейчас рендерит таблицу вручную через `<table>` и локальную логику сортировки (`sortRows`). Это работает, но таблица слабо стандартизирована как переиспользуемый слой: управление заголовками, row-моделью и сортировкой разбросано по компоненту.  
Из proposal следует цель перевести таблицу на единый engine (`@tanstack/react-table`) без изменения продуктового поведения, уже описанного в `web-products-catalog` и `web-products-search-and-create`.

## Goals / Non-Goals

**Goals:**
- Перевести products-таблицу на `@tanstack/react-table` как источник истины для колонок, row-model и сортировки.
- Сохранить текущее пользовательское поведение: набор колонок, сортировка по name/price/rating, подсветка rating `< 3`, пагинация через API и текстовые состояния.
- Упростить расширение таблицы (новые колонки/фичи) через декларативные column definitions.

**Non-Goals:**
- Переход на серверную сортировку или изменение контрактов DummyJSON API.
- Редизайн страницы товаров или замена существующих UI Kit контролов.
- Изменение add-product flow (он остается UI-only).

## Decisions

1. Использовать контролируемый TanStack Table в `ProductsPage`  
Решение: поднять состояние сортировки в React state и передавать его в `useReactTable` через `state`/`onSortingChange`.  
Почему: сохраняет текущую интеграцию с `saveSort/loadSort`, обеспечивает детерминированность и совместимость с remember-me policy.  
Альтернатива: оставить `sortRows` и использовать TanStack только для рендера строк. Отклонено, потому что теряется ценность единого table engine.

2. Оставить клиентскую сортировку в пределах текущей страницы  
Решение: использовать `getSortedRowModel` для уже загруженного page slice, без изменения API-запросов.  
Почему: соответствует текущему требованию "сортировка только на текущей странице".  
Альтернатива: серверная сортировка через API-параметры. Отклонено как изменение продукта, выходящее за рамки change.

3. Зафиксировать колонки как отдельные `ColumnDef<ProductRow>[]`  
Решение: выделить декларативный массив колонок (в компоненте или отдельном модуле) с accessor/cell-рендером, включая red style для low rating.  
Почему: упрощает поддержку и тестирование поведения таблицы.  
Альтернатива: инлайн-описание заголовков/ячеек внутри JSX. Отклонено как менее поддерживаемое.

4. Сохранить текущий визуальный контракт таблицы  
Решение: TanStack используется как headless-слой логики; DOM-структура и стили близки к существующим (`<table>`, `<thead>`, `<tbody>`, текущие токены).  
Почему: минимизирует риск визуальных регрессий и не требует изменений в UI Kit.

## Risks / Trade-offs

- [Риск] Регрессия существующего UX сортировки при смене модели состояния → [Митигация] unit-тесты на toggle сортировки и e2e/integration сценарии для name/price/rating.
- [Риск] Несоответствие persisted sort формату TanStack (`SortDescriptor` vs `SortingState`) → [Митигация] явный адаптер между форматами и тест на восстановление sort после reload.
- [Риск] Повышение сложности `products.tsx` → [Митигация] вынести column definitions и адаптер сортировки в отдельные модули.

## Migration Plan

1. Установить и подключить `@tanstack/react-table` в `apps/web`.
2. Добавить column definitions и адаптер состояния сортировки.
3. Заменить ручной рендер/сортировку на `useReactTable` с сохранением текущего DOM и стилей.
4. Прогнать проверки: типизация, unit/integration для сортировки и отображения колонок.
5. Rollback: вернуть рендер через текущий `sortRows` (изолировано в одном маршруте), если выявлены критичные UX-регрессии.

## Open Questions
