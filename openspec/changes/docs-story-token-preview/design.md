## Context

- `apps/fumadocs/content/docs/design-tokens.mdx` is generated by `scripts/generate-token-docs.mjs` and currently contains static token tables/examples only.
- Existing docs pages use Story client components from `apps/fumadocs/src/stories/*.story.tsx` and render `<WithControl />` in MDX.
- Token docs are regenerated in `apps/fumadocs` predev/prebuild flows, so any interactive preview content must be emitted by the generator (not hand-edited in MDX).

## Goals / Non-Goals

**Goals:**
- Add a reusable token preview story component that demonstrates how token groups affect rendered UI.
- Ensure the generated design-tokens page includes one interactive preview section consistently after each regeneration.
- Keep existing token reference tables and examples unchanged as the primary source of token values.

**Non-Goals:**
- Changing token names, token values, or token metadata schema.
- Replacing existing token reference tables with interactive-only documentation.
- Introducing Storybook-specific tooling or a separate preview framework.

## Decisions

1. Add a dedicated docs story file for token preview (`apps/fumadocs/src/stories/design-tokens.story.tsx`).
Rationale: aligns with established story naming/location conventions and keeps client-side interactive logic out of MDX.
Alternative considered: inline interactive JSX in generated MDX. Rejected because it would duplicate logic and make generated output harder to maintain.

2. Extend `scripts/generate-token-docs.mjs` to emit a stable story import and an `## Interactive` section with `<WithControl />`.
Rationale: `design-tokens.mdx` is generated and would otherwise overwrite manual edits; generator output must include the preview hook.
Alternative considered: post-process the generated MDX in a second script. Rejected to avoid dual generation sources and ordering drift.

3. Keep the interactive preview additive and non-authoritative.
Rationale: token tables remain the canonical value reference; preview exists to aid comprehension and quick visual validation.
Alternative considered: make preview the primary representation. Rejected because table output is easier to diff and audit in code review.

## Risks / Trade-offs

- [Generated MDX structure drift] → Add/update generation checks so expected import + interactive section are asserted in CI/local checks.
- [Preview and tokens become semantically inconsistent] → Keep preview examples generic and token-driven (e.g., `var(--ui-*)`) without hardcoded color/value assumptions.
- [Client-only story import causes docs build issues] → Follow existing story pattern (`.story.tsx` client component + named `WithControl` export) already proven in component docs.
