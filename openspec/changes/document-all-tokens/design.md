# Design

## Context

- UI Kit публикует дизайн‑токены как CSS‑переменные через `packages/ui-kit/src/tokens.css`.
- Документация на Fumadocs сейчас описывает только импорт `@dummy-products/ui-kit/tokens.css`, без справочника “какие токены существуют и что означают”.
- Требование “documented CSS token surface” уже зафиксировано на уровне спеки `openspec/specs/tokens-css-usage/spec.md`, но документирование на практике недостаточно.

## Goals / Non-Goals

**Goals:**
- Иметь страницу документации со **всеми публичными токенами**, сгруппированными по категориям (цвета / типографика / spacing / radius / …).
- Держать справочник **всегда в актуальном состоянии**: токены в документации должны автоматически соответствовать `tokens.css`.
- Дать читателю удобный “reference”: имя, значение, назначение, пример использования.
- Фейлить генерацию/проверку, если появился новый публичный токен без документации (для предотвращения дрейфа).

**Non-Goals:**
- Изменение значений токенов или их нейминга.
- Введение новой токен‑системы/дизайн‑системы, темизации, dark mode и т.п.
- Документирование “внутренних” токенов (если такие появятся) — документируются только **public tokens** из CSS surface.

## Decisions

1. **Автогенерация MDX из `tokens.css`**
- Источник правды для списка и значений токенов: `packages/ui-kit/src/tokens.css` (переменные в `:root`).
- Генератор парсит `:root { --ui-...: ...; }` и формирует MDX‑страницу в `apps/fumadocs/content/docs/` (например `design-tokens.mdx`).
- Группировка определяется префиксами (`--ui-color-*`, `--ui-font-*`, `--ui-space-*`, `--ui-radius-*`) и/или правилами маппинга. Это позволит без ручной правки поддерживать обновления.

2. **Метаданные описаний отдельно от значений**
- В `tokens.css` сейчас нет описаний/семантики токенов; хранить комментарии рядом со значениями неудобно для машинной проверки.
- Добавить/держать отдельный источник метаданных (например `packages/ui-kit/src/tokens.docs.ts` или `packages/ui-kit/src/tokens.docs.json`), где для каждого публичного токена задаются:
  - группа/подгруппа (если нужно),
  - человекочитаемое описание,
  - опционально пример/рекомендации.
- Генератор объединяет “список+значения” из CSS и “описания” из метаданных.
- Генерация (или CI‑проверка) должна падать, если:
  - в CSS есть публичный токен без метаданных,
  - в метаданных есть токен, которого нет в CSS (защита от мёртвых записей).

3. **Интеграция в dev/build**
- Генерация запускается как часть пайплайна документации (predev/prebuild) и/или отдельной командой (например `pnpm docs:generate-tokens`), чтобы локальный dev и CI получали одинаковый результат.
- Сгенерированный MDX файл коммитится в репозиторий для детерминизма и простоты ревью (и при этом всегда может быть пересобран).

## Risks / Trade-offs

- [Парсинг CSS] → ограничить парсер на “переменные внутри `:root`” и поддерживать только декларации вида `--name: value;` (без вычислений), покрыть несколькими тест‑кейсами.
- [Описание токенов станет “вторым источником правды”] → жёсткая проверка соответствия CSS↔metadata и запрет на пропуски.
- [Шумные диффы от генерации] → стабильная сортировка, форматирование и одинаковые переносы строк.
